# autoflow-ide

An issue-based terminal IDE for [AutoFlow](https://github.com/Munsik-Park/autoflow).

You pick an issue, and the IDE runs it through the coordination session of [autoflow-coordinator](https://github.com/Munsik-Park/autoflow-coordinator): the coordination session proposes a workflow, runs AutoFlow modules in work sessions and judges each result. The IDE puts the issues, the run's progress and the sessions on one screen.

Status: early development. The design is in [docs/design.md](docs/design.md).

## The repositories

| Repository | Place |
|---|---|
| [autoflow-module](https://github.com/Munsik-Park/autoflow-module) | The modules: units that each take on one piece of work, each a folder holding a `SKILL.md`, which work sessions run. |
| [autoflow-coordinator](https://github.com/Munsik-Park/autoflow-coordinator) | The coordination session and its tools, which open work sessions in tmux and judge their results. |
| autoflow-ide (this repository) | The screen over the coordinator: issues, runs and sessions in one terminal UI. |

The IDE uses the coordinator through its command-line tools and their output. It does not carry the coordinator's code.

## Requirements

- Python 3.9 or later
- tmux, with the IDE started inside it and a POSIX default shell (sh, bash, zsh), into which `s` and `S` type the line that starts Claude Code
- [autoflow-coordinator](https://github.com/Munsik-Park/autoflow-coordinator) 0.8.0 (any 0.8.0-rcN) and its requirements, including Claude Code and a clone of [autoflow-module](https://github.com/Munsik-Park/autoflow-module), the default modules, named by the coordinator's setting `modules`
- `gh`, signed in, for the issue list
- for browser control (`b`) only: Python 3.10 or later and aiohttp 3.14.5 or later, through the `browser` extra (`pip install -e '.[browser]'`); the IDE runs without it, and `b` then says what to install. On Python 3.9 the extra installs nothing, as the aiohttp releases for 3.9 have known advisories, and `b` says `browser control needs Python 3.10 or later`

## Run

```
pip install -e .
autoflow-ide --repo owner/name          # open issues of a repository
autoflow-ide --workspace <workspace>    # the repository named in a coordinator workspace's repo.json
autoflow-ide --demo                     # placeholder data
autoflow-ide --coordinator <clone>      # every workspace of the coordinator's base
autoflow-ide ... --browser-port <n>     # the port browser control listens on (default: one the system picks)
```

With `--coordinator` and neither `--repo` nor `--workspace`, the left pane (titled `Workspaces`, its column `Workspace / Issue` and its key `1 Workspaces`; with one repository it is `Issues`) lists every workspace of the coordinator's base (`tools/config.py base`, each folder with a `repo.json`), in name order, each under a bold row with its name, and under it the 5 most recent open issues of its repository, newest first, an issue with a run first and marked `●`. An issue that waits for the operator's answer is marked `?` instead, in place of `●` or of the blank of an issue with no run, so a session waiting for an answer is not missed (#79): when a pane of one of its coordination session windows (`<workspace>#<issue>`, see below) shows a Claude Code choice or permission prompt at the window check, every 15 seconds, also before its run is prepared; or when a work session of any of its runs is `waiting-input` in the coordinator's `tools/status.py`, read every 5 seconds. A screen shows a prompt when one of the patterns the coordinator's `tools/terminals` looks for (`Do you want to`, `Enter to select`, `Esc to cancel`, `❯ <n>.`, `Would you like to`) is in its last 12 lines and Claude Code's input area is not on it (a prompt takes its place; a report that quotes those words is above it). After the answer, the next check, or read of the runs, shows the earlier mark again; a window whose screen cannot be read keeps its mark until a check reads it. The pane is where an issue is started and watched, not where the work is chosen (#44). A workspace whose issues cannot be read says why on its row, and the others still show. Each workspace's issues are read with its own token when the workspace has one: `gh-token` in the workspace's folder (the coordinator's WORKSPACE.md > gh-token), passed to `gh` as `GH_TOKEN`, so workspaces of different GitHub accounts show side by side (#74). A `gh-token` the coordinator would refuse (not yours alone, `chmod 600`; empty; not one token on one line) says so on the workspace's row, and its issues are not read. Without a `gh-token`, the issues are read with the GitHub account of the shell the IDE is started from (`gh`, with its `GH_TOKEN` when set): start it where that account is the one you work with. A workspace whose repository that account cannot read shows by its name only, with GitHub's error on its row and no issues, so no run can be started there; that is intended, as work on a repository needs access to it anyway. A token narrowed to a few repositories (such as one kept for working on this clone) hides the others. An issue with more than one coordination session (see `S` below) shows each under its row, by its run's name, or, before its run is prepared, by where its pane is in tmux (`session:index`, or the pane's id when tmux does not list it), marked as the issue is, by its own window and run: a session whose window or run waits is `?`, and the issue is `?` when any of its sessions is. On a workspace's row the run pane is empty and the info shows that workspace; `s` starts nothing there, and Enter folds it (`▸`, with the number of its rows) or unfolds it (`▾`). At start the workspaces with a run and the 3 chosen most recently are unfolded, the others folded; a workspace is chosen by unfolding it or starting a run in it, and dropped by folding it. The choices are kept in `.ide-state.json` at the top of the clone the IDE runs from (ignored by git), or in `~/.config/autoflow-ide/state.json` when it runs from elsewhere. A run that starts unfolds its workspace. A session's rows are hidden with its issue when its workspace is folded. `a` shows only the issues with a run, with their sessions' rows, under their workspaces whatever is folded (the pane's title says `Workspaces · running`, or `Issues · running` with one repository, and the status line `no issue has a run` when there is none), and `a` again everything; with one repository it shows its issues with a run.

An issue that is not among the recent ones is reached by its number, in the workspace the cursor is in (on an issue or on a workspace's row): `#` and the number, then Enter, moves to exactly that issue when it is listed and otherwise looks it up on GitHub and shows it with that workspace's issues (its row says what the number is when it is not an open issue: `(closed)`, `(PR)` or `(closed PR)`, as issues and pull requests share the numbers, and `s` starts only an open issue). Esc closes the box, and with the box closed clears what was found. A found issue is read again at the end of each read of the open issues (below), in the same work, after the list is applied (also when the list cannot be read), so its row and the status line say what it is now, as when it was found: one closed by a merge after it was found shows `(closed)` with no key press. That work runs one read at a time, so each found issue has one read out and its result is applied as it comes back. A found issue that the list just applied shows is drawn from the list and not read on its own; one that leaves the list is read again by the next read. One whose lookup fails keeps what it had, and the status line says why (`issue #12: <gh's error>`, or `issue autoflow-sandbox#12: …` for every workspace) until a later read of it succeeds, Esc clears it, or the next find in its workspace replaces it; a read that comes back after Esc or a new find has changed the found issue is dropped (#80). Searching by words is left for later (#52).

Add `--coordinator <autoflow-coordinator clone>` to show the active runs: the IDE reads the coordinator's `tools/status.py` every 5 seconds and shows each run under its issue. Above the run pane, the coordinator's base (where the workspaces are) and where it was set: `global settings` (`~/.autoflow/coordination.json`), `local settings` (`coordination.local.json` in the coordinator clone) or the `built-in default`, read from `tools/config.py` whenever the issues are read, as the coordinator's settings decide it and the IDE does not change it (#58); then the highlighted issue's repository and its workspace (name, clone and base branch, from the workspace's `repo.json`) and, when it has a run, the run's name, workflow and branch, its worktree and record folder, and where its coordination session is in tmux (session:window and the window's name); before its run is prepared, `run none` and where its coordination session's pane is in tmux (or the pane's id). On a session's row the run pane, the sessions pane, the info, a step's detail and `c` are that session's run alone; on the row of an issue with several sessions the run and sessions panes are empty and the info shows `sessions <N>` in place of the run lines, and the status line `<N> sessions`. Another run's steps and sessions start at the top. Enter on a session's row moves tmux focus to its coordination session's pane; when that pane is gone the status line says so. A run name, base, clone, worktree or record folder too long for the pane is cut in the middle, so its start (where it is) and its end (which run it is) stay in view. The run pane marks a return `↩` and a rerun `↺`, with the step that caused it (`↩ build-2 ← review-1`), as the coordinator's run-status pane does. In the run pane, Enter opens what happened in a step: its state, verdict, result (the status of the module run's end record, `ended`, or `-` while there is none), session and work folder; the Verdict and Notes cells of its row in the run record, which say what work outside AutoFlow did and how the coordinator disposed of a run's findings; and what the module run left in its work folder, as the folder is when the detail opens (#83): its entries, files and folders (marked `/`), sorted by name and numbered. A number key opens an entry over the detail: a file as an output is read (Markdown rendered, JSON indented, other text as it is; the first 512 KB of a long file, #67), and a folder as a list of its own entries, opened in the same way; Esc goes back one level, and from the top to the step. Past the ninth, entries are listed with no key. The coordinator's end record beside the folder (`<work folder>.ended.json`) tells whether the run has ended: an entry it does not list is marked `written after the end` (a folder, when it holds such a file), a file it lists that is gone is not shown, a run with no end record yet is noted as not ended and its entries listed, and an end record that cannot be read, or a folder that cannot be listed, is named under `Could not read` with the reason (the folder's entries are then not listed). `c` goes to the step that caused it. In the sessions pane, Enter moves tmux focus to that session's pane.

The bottom-right corner shows the commit the IDE was started from (`ide 68afb41`), read once when it starts, so an IDE left running on older code after a pull can be told apart; when the IDE does not run from its own clone, it shows the package version.

The open issues are read again every minute, when a step of a run changes its state or verdict or a step is added, and when a run ends (also while another run of its issue goes on), so an issue closed by a merge leaves the list without a key press (an issue that still has a run stays as a "(closed)" row). An issue found by `#` is read again with them (#80). `r` reloads them at once.

`s` starts a run for the highlighted issue, as an operator does by hand: it opens a tmux window named `<workspace>#<issue>` with a shell in the coordinator clone and starts Claude Code there with `Workspace <workspace>, issue #<issue>.` as its first prompt. The workspace is the one in the coordinator's base (`tools/config.py base`) whose `repo.json` names the repository. When the workspace has a `gh-token`, the typed line starts Claude Code with it as `GH_TOKEN` (`GH_TOKEN=$(cat <workspace>/gh-token) claude ...`, as the coordinator's `tools/launch.sh` starts its sessions), so the token is neither typed nor in tmux's arguments; with a `gh-token` it cannot use, `s` opens nothing and says why on the status line (#74). The coordination session then presents the workflow for approval in that window. Before the window opens, a box under the issues asks for instructions for the run (its focus or approach, one line): Enter starts the session with them after the first prompt (`Workspace <workspace>, issue #<issue>. <instructions>`), as typed, with each tab, line break or other space character made a plain space, any other control or non-printable character (as a paste can carry) dropped, and the blanks at either end removed, so the shell the line is typed into cannot act on it; nothing, or only blanks, starts it as before; Esc opens nothing. The box is for that issue and for the key that opened it: while it is shown, `s`, `S`, `#` and `w` do not open it for something else (the status line says what it is open for), as the find and workspace boxes are not taken over either. On Enter, the open is decided from the issue's state read then, and only a state known to allow it opens a session: the issue must still be listed, and open and not a pull request as GitHub gives it then (its state is read at each Enter, since the list can show an issue open for up to a minute after it closed); for `s`, the issue's windows and the runs are read again, and it must have no session and no other open in progress. When one of these refuses it, or cannot be read (GitHub, tmux or `status.py` fails), nothing opens, the box closes and the status line says why. From Enter until the session is open, the open counts as in progress, so `s` meanwhile opens no second one. The instructions are part of the typed `claude --session-id <id> '<prompt>'` line, so they are kept in that shell's history and shown in the process list: put nothing secret in them. The id is one the IDE makes and keeps on the session's pane (`@autoflow-session-id`, for browser control's records, #86); when tmux cannot keep it there, the window is closed, nothing is typed, and the status line says `start <issue>: <tmux's error>`. The line is typed into tmux's default shell, which must be a POSIX shell (sh, bash, zsh), as the coordinator's `tools/launch.sh` needs for its sessions. `s` again, before the run is prepared, goes back to that window, also after the IDE restarted (the window is read again when `s` is pressed; when tmux cannot list the windows, `s` opens no box and says why), and while it is being opened it opens no second one. On a session's row `s` goes to that session, as Enter does; on the row of an issue with several sessions it says so.

`S` opens another coordination session for the highlighted issue, as `s` does (the instructions box, a window of the same name `<workspace>#<issue>` in the coordinator clone, the workspace's token), also when the issue already has a session or a run, and refuses what `s` refuses. The new session shows under the issue at once, with the cursor on it, and its run, once the coordination session prepares it, has its own worktree and branch, which the coordinator makes. A session is its coordination pane: the pane the window opened with, which the coordinator records as the run's coordination surface, so a session keeps its row from the open to its prepared run. Two runs prepared in one pane are two sessions. A second open does not cancel one in progress.

`w` adds a workspace for a repository, as `s` starts a run: give the repository's GitHub address — the web address (`https://github.com/owner/name`), a clone address (`git@github.com:owner/name.git`) or `owner/name` — and Enter (Esc closes the box), and the IDE opens a tmux window named `workspace:<owner/name>` with Claude Code in the coordinator clone and `Create a workspace for <owner/name>.` as its first prompt, with `, cloned from <address>` when the address was more than `owner/name`, so the clone is made the way it was given. The coordination session asks for the rest (the clone, the base branch) and writes the workspace in the base (the coordinator's `WORKSPACE.md`, "Creating"); the IDE does not write it. When a workspace of the base already names the repository, nothing is opened. `w` with the same repository again, before the workspace shows, goes back to that window. The workspace shows on the next read of the issues (`r`, or within a minute), unfolded as one chosen recently; with `--repo` or `--workspace` the IDE shows only its one repository. The IDE does not close that window (#60).

The IDE closes such a window when its issue is done, each window of an issue on its own wait: the issue is closed (asked of GitHub) and has no active run, and 5 minutes have passed since the later of the window's screen last changing and the IDE first finding the issue closed with no run, so a last report is not cut off and the operator can come back to the session after a merge (while it waits for input, its screen does not change, and it still gets the whole 5 minutes after the issue closes) (#28). GitHub is asked again just before the window is closed, so an issue reopened during the wait keeps its window. An issue found open, or whose lookup fails, is looked up again only after 5 minutes. An issue can take several runs, so a run ending while its issue is open keeps the window. The windows are found by their `<workspace>#<issue>` name, every window of that name, so those opened before the IDE restarted are shown under their issue and closed too, and so is one named that way by hand. The status line says when a window is closed; the session can be resumed with `claude --resume` in the coordinator clone.

The status line starts with a notice of something that just happened (a coordination session opened, a window closed, a focus moved, an issue found by `#`), so a narrow terminal does not cut it off, and the notice goes 10 seconds later. Then come the repository, the issue (with what it is when not an open issue: `#2 (closed PR)`) and the run (or `<N> sessions` on the row of an issue with several), and what is true now: the issue and run counts, a read error (of the issues, of an issue with a run, or of a found issue) until the next read succeeds. While browser control runs, or when it could not start, its address or why it could not start is on a row of its own above the status line, so neither a notice nor the rest of the line pushes it out of a 124-column screen (#86).

## Browser control

`b` (not shown in the footer, so every key still fits at 124 columns), or `Browser control: start` in the command palette (Ctrl+P), starts a web server in the IDE's own process, bound to `127.0.0.1` only, and the status line shows its address, `browser http://127.0.0.1:<port>/<token>/`, for as long as it runs. `b` again, `Browser control: stop`, or quitting the IDE stops it: each open page says `server stopped`, and the IDE and every session keep running. When it cannot start (the port is taken, aiohttp is not installed, or the IDE runs on Python 3.9: browser control needs Python 3.10 or later), it starts nothing and the status line says why. `--browser-port <n>` fixes the port, for example to reach an IDE in a remote tmux through `ssh -L <n>:127.0.0.1:<n>`; by default the system picks a free one, so two IDEs can both have it on.

The page follows the IDE's screen: the workspaces and issues on the left, with the same rows, marks (`●`, `?`), folds and `a` filter the terminal has set; the chosen row's info and its run's steps in the middle; the run's sessions on the right. It shows a change at the same read that shows it in the terminal. Clicking a row chooses it in the page only; the terminal's cursor stays where it is. From the page:

- **Start** (`s`) and **New session** (`S`) run the terminal's checks, in its order, and the page's own instructions box asks for the one-line instructions; Enter there is decided by the same checks at Enter as the terminal's box. A refusal, and every other message, is shown on the page that asked and not on the terminal's status line, and a terminal message is not shown on the page. The window of a session started from the page opens with `new-window -d`: the operator's tmux window and the terminal's cursor do not move. A **Start** (`s`) from either side is refused while one of the same issue is opening on the other; **New session** (`S`) is not, as the terminal's `S` is not.
- **Go to session** opens the session's view in the page and moves no tmux focus. The view is the session's pane as tmux holds it, read every half second with `capture-pane -p -e` and `display-message`, which attach no tmux client, so no window's size changes, in any tmux session, also with no client attached. It is drawn with xterm.js at the pane's columns and rows and is read-only: keys typed in it reach no pane. Only text and colours are drawn: a link a session prints shows as its text. When the pane is gone the page says so, as the terminal does, and a pane opened from the IDE is dropped from its issue on both sides.
- **Records** shows the session's screen text and its transcript (Claude Code's session record, the main file and its subagent files). A work session's is the one its run's `sessions.tsv` names. A coordination session the IDE opens is started with `claude --session-id <id>`, the id kept on its pane (`@autoflow-session-id`), so it is found again after the IDE restarts; for one the IDE did not open, the page says `transcript not known: this session was not opened by the IDE`. The id names the transcript of the session the IDE started in that pane: after `/clear`, or `claude` started again there, the session writes another transcript, which the IDE does not know, so the page shows the id, the file's last write time and that note. Each file is sent as its whole records within its last 512 KB, and the page says `<n> bytes before this were left out`, `<n> bytes of a record being written not shown`, or `the last record is over 512 KB: no record shown`. The coordinator clone given as `--coordinator` is resolved to its physical path, the one Claude Code names its folder after.
- **Input**: to a coordination session, a message of at most 700 bytes, entered only into an empty input area (not in copy mode, not over a draft or a dialog) as the coordinator's `submit` enters it, with Enter pressed only once the input area shows it; and to a coordination or a work session, the keys that answer a prompt its screen shows (a digit, the arrows, Enter, Esc). A message is entered as one line, as the run's instructions are: each tab, line break or other space character becomes a plain space and any other control or non-printable character is dropped, so a CR, Ctrl-C or escape sequence in it cannot act as a key press. A work session takes no message, and the coordination session is not told of keys sent to it. When the pane would not take it, nothing is entered and the page says why.

The page shows the text others can write (issue titles, step verdicts, transcripts, screens) as text: it never puts a string from the server in as markup, and a `Content-Security-Policy` lets it run only its own script. Only the page of the IDE that started the server is served or obeyed: every request carries the token, made at each start and shown only on the IDE's status line, with `Host` `127.0.0.1:<port>` or `localhost:<port>`; the WebSocket and every action carry the server's own `Origin`; no action is a GET. A request from another page in the browser, or from a program of another OS user, gets nothing and does nothing. A program of your own OS user is not kept out: it can already drive tmux and read the address from the status line. The server writes no access log, so the token is not logged. Everything the page loads, xterm.js included (`@xterm/xterm` 6.0.0, MIT, in `src/autoflow_ide/web/xterm/` with its hashes), is served by the IDE.

## Tests

`pip install -e '.[test]'`, then `pytest` with the test files to run.

- **CI** (`.github/workflows/test.yml`) runs on every pull request and on main, and a pull request is merged when it passes. It runs only the tests of what the IDE reads from other tools: `tests/test_runs.py` (the coordinator's `status.py` output and `VERSION`), `tests/test_results.py` (a module run's work folder and the coordinator's end record of it), `tests/test_issues.py` (gh output), `tests/test_focus.py`, `tests/test_start.py` and `tests/test_windows.py` (the coordinator's `config.py` and the tmux commands), `tests/test_screens.py` (Claude Code's screens, for the waiting mark, #79, and the input checks, #86), and `tests/test_transcripts.py` (Claude Code's session records, #86). They run on output recorded from those tools (`tests/fixtures/README.md` says from which versions), so they are what breaks when a tool changes.
- **Screen tests** (`tests/test_app.py`, and `tests/test_browser.py` for browser control, which needs the `browser` extra) are not in CI. A pull request runs the ones of what it changes.
- **Browser tests** (`tests/test_browser_page.py`, Playwright in Chromium) are not in CI either: `pip install -e '.[browser-test]'` (Python 3.10 or later; Playwright 1.61) and `python -m playwright install chromium` (the browser of that Playwright), then run them like the screen tests. Two of them set `HOME` to a scratch folder, so set `PLAYWRIGHT_BROWSERS_PATH` to Playwright's browser folder (`~/Library/Caches/ms-playwright` on macOS) when running them.
- **One-off checks**, such as replaying a recorded run against a real `status.py`, are not kept as tests. The pull request states what was checked and the result.
- A new test goes into CI only when it checks what the IDE reads from another tool, on recorded output.
